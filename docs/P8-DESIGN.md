## 1. 目标与边界

面向在 Windows / WSL 中使用多个 Agent 的独立开发者：资源接入后，不必反复维护仓库勾选表；能明确知道信息是否真正送达；操作生产资源时，查询不被反复打断，越界写入被阻止，需要承担后果的操作由人确认。

本阶段是 **Operate** 型界面设计：保留现有视觉、四个导航和两种导航位置，不重做视觉风格，不新增一个复杂的权限控制台。

必须区分四件事：

1. **提供信息**：CloudLink 向某个目录写入哪些资源背景。
2. **允许操作**：经过护栏或执行通道的具体命令是否满足当前策略。
3. **实际同步**：文件是否已经成功写入目标，不能用选择开启、列入或编译成功代替。
4. **真实访问权限**：由 SSH 用户、GitHub / 云平台凭据、系统权限等决定。Skill 的内容选择不是凭据降权，也不能让 Agent 忘记已经读取的信息。

执行通道强制检查的是**经过该通道的调用**。同一系统用户仍可能使用已有凭据和其他工具直接访问资源；本阶段不承诺安全沙箱或防刻意绕过。

## 3. 顶栏：原生系统栏 + 应用导航（原型外观已认可，原生行为待验证）

用户明确选择保留最上层原生系统标题栏：应用图标、CloudLink、最小化／最大化／关闭由系统提供。下层移除全部自绘窗口按钮及它们前面的竖向分隔线，只承担应用导航与搜索、导航位置、添加、更新等操作。不增加标题栏模式设置。

下层排列（第一轮原型已认可）：顶栏导航模式不再重复显示 CloudLink，导航靠左、操作靠右；下层保留现有 48px 高度。侧栏模式也去掉重复应用名，导航条目不变。真实应用的上层系统栏高度由系统与 DPI 决定；静态原型用 32px 占位来演示配色衔接，不把该模拟尺寸作为原生实现规格。

### 上下配色衔接

- 两层以同一组现有画布背景令牌为目标，浅色一起用浅灰，深色一起用深灰；不新增品牌色、渐变或装饰阴影。
- 应用主题选择必须同步到原生窗口，不允许只把 WebView 改成深色、标题栏仍留在浅色。启动、手动切换、跟随系统与窗口激活／失焦状态都要考虑。
- Tauri 的窗口主题支持浅色／深色切换；精确的原生标题栏配色不是 CSS 或 WebView `backgroundColor` 自动完成的。Windows 11 提供 DWM 标题栏背景／文字颜色接口，具体映射和调用留到实施规格。
- Windows 10 或不支持相应能力时以系统浅／深主题协调为兜底，不承诺所有系统逐像素同色；系统高对比度／辅助功能优先，不能为了同色牺牲文字与按钮识别。
- 应用不额外给两栏交界增加分隔线或阴影；导航下缘保留与内容区的一条发丝线。原生系统边框若无法消除，不为视觉无缝而重新自绘整套系统按钮。

### magpie 的已核对做法

本机 magpie 参考版本 `9298d2a7` 保留 Windows 原生标题栏，`internal/gui/assets/app.js:3983–4002` 读取页面实际背景色，在主题变化后请求标题栏着色；`internal/gui/titletint_windows.go:14–30` 同步系统栏浅／深模式、标题栏颜色和调整窗口尺寸时露出的底色。`windowChrome`（同文件 38–54 行）还预置启动时及激活／失焦时的匹配背景，避免等待页面加载才修正颜色。

CloudLink 采用同一种产品效果：系统负责窗口，应用负责与页面协调配色；补齐启动和切主题状态，不仅静态截图颜色接近。magpie 使用 Wails，CloudLink 仍使用 Tauri，不能原样复制它的框架调用或绕过依赖白名单。仓库官网截图未包含原生 Windows 外框，只能作为表面与控件密度的参考，不能替代原生行为证据。

当前主配置是 `decorations: false`，属于旧方向。实施时需要统一正式包与桌面测试配置，保留真实原生窗口装饰；不能只删除下层按钮，导致另一些构建没有窗口控制。

验收关注真实桌面窗口，不只看浏览器 Mock：

- 最小化、最大化／还原、关闭只出现在最上层，由系统反映真实状态。
- 原生拖动、双击最大化、边缘缩放、系统快捷键与受支持的 Windows 窗口布局行为不退化。
- 下层导航交互不误触拖动；原生关闭仍遵循「留在托盘／退出」。
- 主题切换、启动首帧、窗口失焦、默认／最小尺寸、两种导航位置均验证；原型可模拟配色关系，但不能代替真实 Windows 标题栏验证。
- 官方参考：[Tauri WebviewWindow 主题 API](https://docs.rs/tauri/latest/tauri/webview/struct.WebviewWindow.html#method.set_theme)、[Windows DWM 窗口属性](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwmwindowattribute)。

## 4. 资源详情整体编辑（弹窗形态已明确，`p8-clean-v9` 样式待查看）

用户认可第一轮原型的视觉，但明确指出：要解决的是整项资源信息的编辑修改，不只是名称。用户通过 magpie 截图进一步明确：「分页」指覆盖在当前详情上的小编辑窗口，不是离开详情进入二级页。不能以标题重命名代替完整信息维护，也不能再按跳页实现。

### 4.1 更多入口与当前页编辑弹窗

采用「详情以查看为主 → 更多选择编辑任务 → 居中弹窗修改 → 保存后关闭」的流程。原详情始终保留在背景，导航和当前位置不变；背景罩灰且不可交互，不新增一级导航、浏览器标签或独立编辑页。借鉴 magpie 的浮层结构，保留 CloudLink 已认可的视觉与配色。

「更多」按任务提供入口，不按每个字段拆出一长串菜单：

- **编辑连接**（SSH 资源排第一）：SSH 别名、地址、端口、登录用户、认证方式、跳板机等；复用既有连接编辑与验证规则。
- **编辑资料**（排在编辑连接之后）：名称、用途、承载的站点、标签、云厂商／地域、笔记、红线，以及服务和关键目录的人工描述。服务／目录信息的编辑删除只是修改 CloudLink 记录，不是停止或删除远端服务；普通资料修改不触发重连、清空验证或更改连接标识。CLI 资源不显示 SSH 专属的编辑连接入口。
- 复制别名、预览 Skill、重新探测和删除等现有操作按原有职责保留，与编辑入口分组。

弹窗的三段结构：

- **固定顶部**：编辑任务标题、当前资源名称与别名、关闭按钮；不放「返回上一页」导航。
- **中间滚动**：按「基本信息」「服务与目录」「红线与笔记」等分组，常用项展开、少用项折叠，不把每个字段变成一个分页。展开分组、添加记录、聚焦错误字段时只滚动正文，不能带走标题和底栏。
- **固定底部**：影响说明与统一「取消／保存修改」；连接编辑使用「取消／保存连接」。最小窗口仍保留外边距和完整操作区，不能让弹窗越过系统标题栏。

**样式与添加弹窗一致（2026-11-13 用户指出上一版配色不协调后修订）：** 上一版是 720×600、白标题栏／灰正文／带边框白卡片／白底栏的多层结构，与已有添加弹窗是两套做法。`p8-clean-v9` 改为：

- 整个弹窗一个底色（卡片色），正文不再用灰色画布；表单字段直接排在弹窗上，不套带边框的卡片。
- 只有列表型内容保留细边框和 10px 圆角：折叠分组、红线与笔记、仓库勾选列表，与添加弹窗里「高级」的做法相同。
- 宽 600，高度随内容，最高 600；标题 14px、下方无分隔线，分组小标题 12px 次要色，底栏上方一条浅发丝线。
- 正文滚动条用与添加弹窗相同的细滚动条。「管理仓库范围」「接入 GitHub」用同一套样式。

所有输入先作为草稿，不即时改动背景详情。保存成功关闭弹窗，更新同一资源详情并保留原滚动位置；保存失败保持弹窗与全部输入。无修改时，取消、关闭、Esc 或点击遮罩直接关闭；有修改时在**同一弹窗底部**切换为「继续编辑／放弃修改」确认，不叠第二个弹窗。确认期间正文不可编辑；Esc 回到编辑，不直接丢弃草稿。焦点限制在弹窗内，关闭后回到原入口；Ctrl+S 在正常编辑状态提交，放弃确认期间不提交。

档位和 Agent 选择仍为独立即时控制，不混入普通资料的保存。操作系统、硬件、探测时间和连接状态等采集事实通过重新探测／检测更新，不直接伪装成可编辑资料。云平台详情沿用同一种编辑结构，但不显示 SSH 专属字段，账号与范围流程另行设计。

用户已明确上述更多入口、完整编辑范围和当前页浮层形态；`p8-clean-v9` 的样式待用户查看，数据契约、迁移和真实连接实现另行细化。导入服务器仍遵守既有连接只读边界，不能因为新增编辑入口而重写用户自己维护的 SSH 配置。

### 4.2 名称快捷编辑（原型已有，不能代替完整资料编辑）

名称原地修改作为轻量快捷操作保留，完整信息维护以编辑弹窗为主。用户要求符合人的第一直觉，同时保持清新简洁。对照 magpie 的账号名称交互后，撤回「常驻铅笔 + 保存／取消」建议，改为轻量的文字原地编辑：

- **平时**：仍是普通标题文字，没有输入框边框、常驻铅笔或一排操作按钮。
- **悬停／键盘聚焦**：以淡虚线下划线及「点击重命名」提示表达可编辑；键盘焦点仍有清楚的焦点环，不只依赖 hover。
- **开始编辑**：单击名称，原位置变为同字号的单行输入框并选中名称，方便直接替换。键盘可聚焦并用 Enter 进入；不要求双击，也不打开对话框。拖选名称复制时不误触编辑。
- **提交**：Enter 或失焦保存有效且已变化的名称，回到文字状态；不在输入停顿 600ms 时提前提交半截名称。Enter 随后引发的 blur 不能重复提交。
- **取消**：Esc 恢复原名，只退出编辑，不返回资源列表；取消引发的 blur 不能把草稿保存。中文输入法正在组词时的 Enter 不提交。
- **失败／无效**：保留输入并就地说明原因，不能静默丢失草稿或提示已保存；空白名称不自动替换成 IP。成功沿用短提示与撤销，不留下常驻成功标签。
- **可发现性兜底**：「更多 → 编辑资料」包含名称字段，不再单独堆一条「重命名」菜单；直接点击标题仍是小改名称的快捷操作。

名称是资源信息，不属于连接认证流程。只改名称不能清空连接验证、触发重新连接、修改别名或迁移 SSH 信任记录。保存成功后标题和列表同步更新；下方「Agent 需要知道的」不再重复提供名称输入框，已有连接的编辑表单不承担重命名。

导入服务器同样能修改显示名称，原 SSH 配置不动；云平台显示名称沿用同一种交互，账号绑定和 CLI 标识不随之改变。长名称、正在保存、失败、取消、键盘焦点和最小窗口均需在原型中表达，名称输入框不能把右侧操作挤出窗口。

参考：本机 magpie 源码版本 `9298d2a7` 的 `internal/gui/assets/app.js:13383–13411`（`accountNameButton`：点击编辑、Enter／blur 保存、Esc 取消、拖选保护），以及 `app.css:2536–2544`（无框文字、悬停淡虚线、紧凑输入框）。该模式原本用于账号显示名称，不宣称 magpie 的所有标题都可编辑；CloudLink 借鉴交互，仍使用 PRD 第七章指定的组件和表单机制，并补齐上述中文输入、失败保留和键盘行为。

### 名称与 SSH 别名（2026-11-13 已确认）

保留底层职责区别，但只让用户日常关心一个名称，不要求命名两次：

- **名称**是界面里唯一主要的资源称呼，支持中文。标题快捷修改与「编辑资料」里的名称是同一个字段，不是两套命名。
- **SSH 别名**用于终端连接，不作为另一项常规命名任务；新资源由系统自动生成稳定、唯一且不含地址的别名。新增和「编辑连接」均收进默认折叠的「高级」，需要自定义快捷连接名时再修改，编辑连接里可以直接复制。
- 修改显示名称不联动修改 SSH 别名，避免已有命令、脚本和连接引用失效；已有自定义别名和导入别名保留，不做静默替换。手动改别名时就地说明已有命令和脚本也需调整。
- 新增表单的名称可留空，提示将使用的中性名称。连接过程标题使用显示名称，而不是把自动别名重新提升成主要称呼；SSH 配置说明等需要实际命令的地方仍可显示别名。
- 新别名与地址、显示名称解耦；修改地址或名称、切换登录方式、返回表单时不重新生成。已占用别名不能保存，错误定位到高级内对应字段。

这一层级已在原型中（现为 `p8-clean-v9`）；菜单仍为编辑连接在前、编辑资料在后。原型用「服务器 1 / cloudlink-1」演示中性命名与不重复，正式唯一标识生成和历史数据迁移另写工程规格。

### 缺省名称与隐私

新建名称可留空，但默认值不能直接使用连接地址，也不能把 IP 变形成自动别名后当作「没有导出 IP」。已确认生成不含地址的中性显示名称及稳定标识；保存后不随名称或列表顺序自动变化。

不通过默认开启连接信息导出、放宽密钥／地址检查解决编译受阻。已有资源不能批量静默改别名；历史默认值的识别、提示与用户确认迁移需在详细规格中补齐。

## 5. GitHub：持续发现，而不是静态勾选表

### 5.1 已确认的产品语义

- 默认自动跟随**用户明确选定的所属账号／组织**；不是无边界收集所有公开仓库，也不是自动扩大到后来加入的所有组织。
- 范围含其中当前及未来有权访问的仓库，包括有权访问的私有仓库；首次选择时写明。
- 可以排除个别仓库，也可以切回「只同步指定仓库」。排除只约束 CloudLink 提供的信息及其受管操作范围，不撤销 gh 的真实访问权限。
- 新增仓库无需再回来勾选；自动发现不改变账号的档位，也不构成对某次写操作的批准。
- 老版本已有的手选范围先保留为手动模式；用户选择自动跟随后才扩大，升级不能悄悄纳入更多仓库。

### 5.2 归属分组与页面结构

**2026-11-13 已确认：** 个人账号、每个选定组织各自作为一项 GitHub 资源。登录身份与仓库归属分开：一个登录身份可以供多个归属使用，但不能由此把它有权访问的全部组织自动纳入。每项资源仍是一套生产标记、档位和 Agent 选择，不扩展为每个仓库一个档位。

据此制作的页面方案（已在原型中，弹窗样式见第 4 章）：

1. **新增 GitHub**：在同一添加弹窗中选择一个归属，已接入的标明且不能重复添加；随后进入仓库范围配置，默认自动跟随，清楚说明当前／未来及有权访问的私有仓库也在范围内。默认只读，按已有新资源规则同步给已启用目标。共用已有登录身份，不要求为每个组织重复登录。
2. **资源首页与详情标题**（2026-11-13 用户纠正）：默认名称仍为 `GitHub`，不能把「按归属分开」做成大号的 `GitHub · <用户名／组织>` 标题。只有首页存在多个 GitHub 资源时，才在副行用现有 12px、muted 的小字区分归属；仅一个时保留原来的安静资源行。详情在标题下的状态行及「仓库范围」里说明归属，不与主标题争层级。显示名称可以单独修改，改名不换账号／组织。
3. **详情中的仓库范围**：设置式列表，显示归属、当前使用的登录身份、自动跟随／手动选择及排除或选中数量；组标题右侧「管理范围」。档位和 Agent 选择继续独立控制。
4. **管理范围**：当前页居中弹窗，固定标题与保存／取消底栏。复选框在两种模式下一律表示「提供给 Agent」：自动模式取消勾选即排除，手动模式只提供勾选项；避免切换模式后勾选含义相反。可搜索，排除项标明「已排除」，本次扩围的行标明「将新增」。首次从自动切到手动时先保留当前纳入的已知仓库；在同一草稿中来回切换时保留先前的手动选择。由手动切到自动时说明会纳入未来仓库及私有仓库，保存前显示新增的当前仓库数，不静默扩大。
5. **仓库列表**：搜索、刷新，以及仓库名／默认分支／可见性／部署目标四列；自动模式的普通查看列表不要求逐行勾选。无匹配与未选择任何仓库分开说明。关系仅显示来源，不联动授权。
6. **失败与迁移**：部分结果、离线、归属权限不足时保留历史记录并标注，不把没取回的仓库视为已删除；可以收窄范围，完整核对前不能扩大。保存失败保持草稿，关闭保护未保存修改。旧版已手选的范围按原样进入手动模式，只有显式选择并保存后才转自动。

文案用「提供给 Agent 的仓库信息」，避免「没勾选就看不见」「已经授予 GitHub 权限」等无法兑现的表述。上述交互的原型不代表已完成真实 gh、多身份／多环境权限核验或分发。

### 5.3 新鲜度与权限

Skill 应提供身份、允许发现的范围、查询方式、规则和已知的关键关系；不能只给一次生成的仓库名单。Agent 在仓库任务中按需查询最新信息，生产资源的发现／查询同样走通道。不把所有仓库详情塞进常驻上下文，也不要求 CloudLink 窗口一直打开才能发现新仓库。

建议应用在进入 GitHub 详情时按需刷新，自动刷新有节流，手动刷新可立即执行；Agent 发起实际操作时另行核验，不能把 UI 缓存当成授权依据。具体刷新间隔与命令契约需在详细设计中定稿。

必须覆盖：

- gh 当前实际凭据可能受环境变量影响；「所属 owner」不是「登录身份」。不以用户名或 `gh auth status` 的单个成功提示推导全部仓库权限。
- Windows 与 WSL 可能使用不同账号／不同权限，不能用一个环境成功代替其他环境可用。
- 列表有分页、数量限制或部分组织不可访问时，明确显示「部分结果」，不能宣称已列出全部可访问仓库。
- 断网、限流或检测失败不等于仓库已删除；保留最后一次快照并标记过期／不完整，不据此扩大范围。
- 仓库稳定 ID 用于跟踪重命名；转移到未选所属范围后不能无提示继续纳入。排除项不能因重命名失效。
- 凭据无权访问时说明应在 GitHub 调整授权；CloudLink 的信息选择开关不能修复真实权限不足。

### 5.4 仓库与部署目标

基于 Vercel 项目绑定、Cloudflare Pages 来源及受限的服务器工作目录 remote 信息建立关系，显示证据来源，允许隐藏、改写和补充。

关系不是自动授权：不能自动改变目标的生产标记、档位或分发选择；某份 Skill 中未提供的资源，不能借关系文字泄漏。远端元数据仍按不可信输入清洗，remote URL 中的凭据不得写入文档或日志。

通过普通 Git 推送或外部 CI 间接触发部署，不因存在关系图就自动纳入强制拦截保证；具体 GitHub 写操作的判定范围要明确列出。

## 6. 执行通道与审批（保留原交互，工程提案见第 11–12 章）

保持两个档位，不增加一个用户需要理解的「执行通道档」。生产资源的操作入口稳定，档位只影响判定。

**以下判定矩阵只适用于 CloudLink 运行中（包括托盘）。** 按 D10，彻底退出后 CloudLink 不再执行这套命令检查或审批；Skill 中仍可保留档位、红线和范围作为给 Agent 的指令，但不能宣称它们此时仍由 CloudLink 强制执行。

| 操作 | 只读巡检 | 标准运维 |
| :--- | :--- | :--- |
| 已支持、目标明确的查询 | 通过 | 通过 |
| 普通写操作 | 拒绝，说明需切换档位 | 通过 |
| 可判定的高危操作 | 拒绝，不能用审批绕过只读档 | 请求允许一次／拒绝 |

| 资源、身份或目标无法可靠确定 | 拒绝并提供可操作说明 | 拒绝并提供可操作说明，不默认为安全 |

现有 hook 对解析不了的命令是放行并记为「未能解析，已放行」；通道在生产资源上改为上表的行为，非生产资源的既有行为不变。「查询不被反复打断」要靠样本保证：验收样本集须包含真实的只读查询（管道、`docker exec`、`journalctl`、`kubectl get` 等常见写法），这些在只读档必须能解析并通过，不能靠拒绝来凑「漏放行 0」。

### 审批卡

**2026-11-13 用户确认 D12：审批交互使用原来的。** 保留「动态 → 等你确认」及现有卡片结构：发起方与资源 → 命令 →「允许一次／拒绝」。不新增审批页，不重排卡片，不另加原因面板、倒计时模块或第二轮确认。

完整命令仍须可读，不隐藏影响判定的参数；必要上下文与结果沿用已有说明、展开信息及操作记录位置，不借此重做布局。系统通知只定位到对应卡片，不直接批准，也不在通知里泄漏命令细节。

### 状态与不可逆性

- 区分待审批、已拒绝、已超时、已取消、已批准待执行、执行中、执行成功、执行失败、结果未知。
- 「允许一次」不是「执行成功」；旧 hook 只知道放行时，应显示「已放行」，不能推断真实执行结果。
- 命令开始产生副作用后不能用「撤销」假装回滚。审批没有永久允许或整批一键放行。
- 审批请求自创建起 5 分钟到期，到期按拒绝处理。Agent 的单次命令调用通常等不了 5 分钟（常见默认约 2 分钟），所以等待分两段：`exec` 内联等一小段，没等到就返回请求编号，Agent 再用 `wait` 继续（第 11.1、12.2 章）。重复点击、迟到答复、重复请求不能造成多次执行。
- 审批绑定本次资源、环境、身份、命令与必要输入；执行前重检策略。命令、文件、目标或策略已变化时，旧批准不能继续使用。
- 切回只读、撤回资源、停用目标时，尚未执行且已不符合条件的请求作废；已经运行的远端任务不承诺自动回滚。

### 应用与任务生命周期

**2026-11-13 用户已明确选择 D10：彻底退出时，也停止 CloudLink 命令检查。** 已分发的 Skill 仍可读取、调用，不能强制要求重新打开 CloudLink 才能正常使用。

- **窗口关闭但留在托盘**：仍在运行，检查与审批继续。
- **彻底退出**：CloudLink 不再按只读／标准档检查命令，也不请求 CloudLink 审批；Skill 与正常 SSH／CLI 用法保留。命令仍受远端账号权限及 Agent 自身权限机制约束，不是权限凭据被提升。
- **调用入口不能失效**：若 Skill 写的是 `cloudlink exec`，退出后该独立入口仍须可用，不能返回「打开 CloudLink 才能执行」。独立转发、运行状态识别以及与现有 hook 的分工见第 11 章；不靠退出时删除 Skill 或反复卸载 hook 来实现。
- **明确退出不等于批准旧请求**：建议取消仍在等待、尚未执行的审批请求，不把退出当作「全部允许」，也不在下次启动后自动执行。已执行的远端操作不承诺回滚。
- **恢复运行**：对后续请求恢复当前设置的检查，不追溯拦截已完成的操作。界面与 Skill 必须如实说明「退出后 CloudLink 检查停止」，不能沿用「关着也始终有护栏」的承诺。

此决策尚未实施。正式 PRD、PRODUCT.md 与既有护栏退出行为需在设计定稿后统一修订；不能继续将旧版「独立护栏始终检查」作为 P8 的约定。运行状态不明、崩溃和更新交接的具体行为仍需在工程规格中明确，不能简单把一次 IPC 失败当作已退出并放开检查。

交互终端不在 P8 范围。文件传输、长任务、取消、输出上限、连接中断后的结果未知与应用更新期间的行为，必须在工程详细设计补齐，不能只提供 `exec` 外壳就声称完整支持。命令执行的实时输出与持久操作记录分离，不默认保存原始输出到日志。

### GitHub 判定边界

按具体子命令、参数、身份与仓库判定，不能仅靠包含 `gh` 或 HTTP GET 判断安全；凭据输出、仓库删除、默认分支强推等原有红线需逐条对照官方 CLI 能力落实。查询元数据与读取凭据值不能混为一谈。普通本地 Git 操作不扩大纳管，沿用原规划明确的高危 Git 范围。

### 7.1 CloudLink 当前无法写入且误报的源码根因

1. **父级目录链接被一刀切拒绝**：`cloudlink/src-tauri/src/deliver/paths.rs:95-113` 的 `reject_link_ancestors(path)` 遍历 `path.ancestors()`，只要任意祖先（包括 `~/.claude/skills`、`~/.agents/skills`、`~/.trae/skills`、`~/.kiro/skills` 本身或其上层，例如 Mirasim 等工具创建的软链接或 Windows Junction）带有 `is_symlink()` 或 `FILE_ATTRIBUTE_REPARSE_POINT`（`0x400`），就立即报错 `PermissionDenied ("delivery path contains a link or reparse point")`。
2. **父级链接错误被误报成「同名冲突」**：`cloudlink/src-tauri/src/deliver/mod.rs:73-76`（`inspect_path`）与 `:100-108`（`inspect`）将 `reject_link_ancestors` 的 `PermissionDenied` 统一映射成 `DeliveryStatus::Conflict`，导致界面显示 `"目录里已有同名 Skill"`。
3. **未实际写入却弹出「已同步」Toast**：`cloudlink/src-tauri/src/ipc/assets.rs:421-486` 的 `set_distribute` 调用 `publish_locked()` → `deliver::sync_auto`（`deliver/mod.rs:270-275`），遇到 `DeliveryStatus::Conflict` 时静默跳过写入并返回 `Ok((checked, None))`，前端 `actions.ts:63-80` 只要 Promise resolve 就弹成功提示。

### 7.2 对标 Magpie 与 CC Switch 的底层解决方案

对照本机 `magpie`（`internal/library/skills.go:347-514`）与 `cc-switch`（`src-tauri/src/services/skill.rs:564-648`）：

- **允许父级 `skills` 目录是 Symlink / Windows Junction**：对目标 `skills` 父目录逐级解析符号链接与 Windows Junction（参考 Magpie `realDir` / `realBelow` / `resolve`，设置递归深度上限 40 防环，并校验解析后的真实父目录不与 CloudLink 数据根、编译源目录或 `~/.ssh` 重合），然后在解析后的真实父目录下操作叶子目录 `cloudlink-servers`。
- **叶子安全检查绝不放宽**：仅对叶子目录 `<real_skills_dir>/cloudlink-servers` 本身及其内部文件执行 `symlink_metadata` + `FILE_ATTRIBUTE_REPARSE_POINT`（`0x400`）与 `.cloudlink.json` 所有权校验。叶子本身若是非受管同名目录或外部链接，仍报真实的同名冲突，需用户显式「备份并接管」，绝不跟随叶子链接覆写或删除外部目标。
- **多 Agent 指向同一真实父目录时按一个分发单位处理（D13）**：不在 UI 新增「共享目录」行或弹窗；后端按真实父目录分组（类似 Magpie `skills.go:465-503` 的 `sharers`），组内写一份 `cloudlink-servers`。资源的开关对整组生效：给组内一个 Agent 开启，其他成员一起点亮并在提示里说明共用目录；关闭同理。不做「各自开关、后台取并集」，那样会出现图标未点亮而对方实际能读到的情况。细则见第 13 章。
- **真实写入反馈**：区分真实的「同名外部 Skill 冲突」（`Conflict`）与「写入失败／路径异常」（`Error`）；`set_distribute` 与自动同步仅在目标实际写入成功时提示「已同步」，若目标跳过或失败则如实反馈原因。

## 11. 独立调用入口与运行状态

### 11.1 程序与调用协议

复用已有 console sidecar `cloudlink-guard.exe`，在保留无子命令的旧 hook 协议之外新增子命令。不让桌面 GUI 可执行文件承担终端标准流，不要求修改用户 PATH。文档中的 `cloudlink exec` 是产品层简称；Skill 实际写入**该环境可调用的、经正确引用的 sidecar 绝对路径**。

建议协议：

```text
<runner> exec --env <envId> --asset <assetId> [--tool git] [--timeout <seconds>] -- <command>
<runner> wait --env <envId> <requestId>
<runner> discover --env <envId> --asset <githubAssetId>
<runner> put --env <envId> --asset <serverId> -- <localFile> <remoteFile>
<runner> get --env <envId> --asset <serverId> -- <remoteFile> <localFile>
<runner> status
```

- `assetId` 使用现有稳定资源 ID，不把显示名称或连接地址当路由主键，也不向用户新增第三个命名字段。改名后旧调用仍指向原资源，删除后不能因复用别名而指向新资源。
- SSH 的 `<command>` 恰好是一个远端命令字符串；云 CLI 则保留 `--` 后的 argv 向量，不拼接成 shell 命令。四家 CLI（`gh`、`wrangler`、`vercel`、`oci`）的程序由资源的提供方决定，不靠参数指定；`--tool git` 只用于 GitHub 资源上已定义的高危 git 范围，不是任意本机程序执行器。
- **审批分两段等待**：`exec` 遇到需要审批的命令，最多内联等约 90 秒；用户在此期间答复则照常执行并返回输出。没等到就以专用状态返回 `requestId` 和「等待用户确认」，不算失败也不算拒绝。Agent 随后调用 `wait <requestId>`：批准后由这次 `wait` 调用执行命令并拿到输出；仍未答复则再次返回等待。请求到期、被拒绝或已被消费时返回对应状态。Skill 里写明这一流程，并提示不要因等待而换别的途径重发命令。
- 参数、帧格式、路径和资源路由有效性始终校验。这是程序正确性，不是 D10 关闭的命令策略检查；退出后也不能把未知资源 ID 当作主机地址尝试连接。
- CLI 不读 SQLite 或原生密码库。桌面侧维护带版本、所有权、原子写入和访问权限的私有路由目录，存资源 ID 到 SSH 配置／CLI 环境与默认账号的映射；密码、私钥内容不进入该目录。
- runner 从自身受管 `bin` 的父目录定位数据根，沿用当前 sidecar 的隔离方式；不能因为测试配置缺少文件而回退真实 HOME。缺少路由、CLI、密钥或 WSL 互操作时返回具体不可用原因，不以「请打开 CloudLink」代替诊断。
- Windows 用系统 OpenSSH 的绝对路径；WSL 经已验证的互操作入口转到指定发行版。WSL 互操作关闭时如实报告该入口不可用，不假称已覆盖；原有手动 SSH 不改。必要的环境能力检查在分发前完成。
- SSH 使用 `-T`、`BatchMode=yes`、已信任主机密钥检查和别名前的 `--`。导入主机的配置仍由用户维护；执行用私有快照／配置，不撤下公共别名，不把 `\\?\` 路径传给 OpenSSH。
- CLI 查找可以复用现有 Login Shell 检测，但任意执行请求不能拼进 Login Shell。执行使用已解析的程序路径与 argv；Windows 的 npm `.cmd` shim 单独适配并做引号／元字符样本测试，禁止简单开启 `shell: true`。
- 默认不提供 TTY，`exec` 不接收不透明 stdin 脚本；文件输入走具名传输入口。原始 stdout / stderr 有界缓冲后流式返回，子进程退出码透传，不默认落盘。CloudLink 自己的拒绝与失败另外带来源和错误 ID，不能仅靠某个退出码判断是否被护栏拒绝。

### 11.2 GUI 运行状态不是靠一次连接失败推测

增加受管 `runtime.json`（协议版本、安装身份、会话 epoch、PID 与进程创建标识、临时 loopback 端点、状态）。启动早期先登记 `starting`，策略与协调器准备好后才为 `active`；关闭到托盘不改变它。退出路径先进入 `stopping`、取消未启动的审批，再记录 `stopped`。不反复安装／卸载用户 hook，不重写已分发 Skill 来切换状态。

| 可核实的状态 | 新调用的行为 |
| :--- | :--- |
| `active`，含托盘 | 按当前策略检查；需要审批的请求进入既有审批流程 |
| `starting` / 更新交接中 | 短时等待就绪，超时返回「入口暂未就绪」；不当作退出跳过检查 |
| `stopped`，且对应进程确已结束；或旧会话进程确认不存在 | 按 D10，不进行 CloudLink 命令检查／审批，入口仍独立转发；不要求重新打开 GUI |
| 进程仍活着但协调器不可达，或身份／状态无法可靠确认 | 返回运行状态异常，不用一次 IPC 失败当作退出；不自动重发有副作用的命令 |

- PID 必须与创建标识及安装身份一起核对，避免 PID 复用。跨测试实例、跨安装的端点不能互相接受请求。没有有效会话记录时，用按数据根区分的实例存活标识辅助判断：确认不存在才是未运行；标识存在或无权检查时仍属 starting／unknown，不因缺少一个文件就跳过检查。
- 运行状态检测使用小型平台封装，复用已有 Win32 FFI 模式；不为每条命令启动 PowerShell 来查进程。新平台依赖若超出白名单，必须另行申请，不能自行添加。
- 崩溃后确认进程已不存在，新调用按退出处理；此前已发出的请求按其生命周期收束，不能因崩溃重新执行。状态记录损坏与「进程不存在」不是同一结论。
- 正常退出前已启动的独立命令不交给桌面 `cancel_all_jobs` 一并杀掉。桌面自己的连接测试／探测仍按原规则取消；远端任务是否停止不能靠关闭本地窗口保证。
- 退出后新调用不记作「经过 CloudLink 检查」，不伪造审批或执行成功记录。已在运行时开始的请求可以补完自身结果。UI 与 Skill 的覆盖说明必须反映退出边界。

### 11.3 hook 与 runner 的分工

- **不重复判定**：hook 认出命令是受管 runner（按受管 `bin` 的规范化绝对路径比对，含 WSL 下的对应路径）的 `exec`／`wait`／`put`／`get` 调用时直接放行，判定和记录都由 runner 做。仅凭文件名相同不算受管 runner。
- **生产直连的识别**：hook 按受管别名和 CloudLink 记录的地址识别对生产资源的 `ssh`／`scp`／`sftp` 直连，拦截并引导改走 runner。用户自有别名、未登记的地址、经其他工具发起的连接识别不到，界面与 Skill 如实写明不保证。
- **同一套运行状态**：hook 与 runner 共用第 11.2 章的状态判断，实现放在两者共用的 crate 里，不各写一份。hook 每次调用只读一次 `runtime.json` 并做一次进程核对，不启动子进程。按 D10，确认已退出时 hook 也不再拦截。
- **不让 Agent 顺手关掉检查**：CloudLink 运行时，结束 CloudLink 进程、改写或删除 `runtime.json`／`policy.json`／路由目录的命令列为红线，没有「允许一次」。定位仍是防手滑，同一系统用户刻意绕过不在承诺范围内。
- **更新时替换 sidecar**：`exec` 可能长时间运行，Windows 上运行中的 exe 不能被覆盖或删除，但可以改名。更新受管 `bin` 时先把旧文件改名为带版本的旧名，再写入新文件，旧文件在下次启动且无进程占用时清理。改名失败则保留旧版并报告，不留下半份文件；已在运行的旧版调用按旧协议版本完成，协调器在一次更新内兼容上一协议版本。

## 12. 审批协调与请求生命周期

### 12.1 通信与权限分工

GUI 协调器仅绑定 `127.0.0.1:0`，不对局域网开放。复用一次性能力与有界消息的做法，但审批不复用密码 broker 的 token 或命名空间。每次启动独立会话身份；请求帧有版本、长度上限、短连接超时，取消与断开可检测。

CLI 可以提交请求、查询自己的请求、取消自己的请求；**不能调用允许／拒绝接口**。允许／拒绝只由现有 Tauri GUI 命令处理，仍只经 `ipc.ts`。不接受命令行中的 `--approved`、调用方自报的「用户已同意」或任意本地 JSON 文件作为批准。这个设计防止意外自批，不把同一个 OS 用户包装成安全隔离。

请求快照至少绑定：`requestId`、会话 epoch、资源 ID、环境、调用种类、解析后的目标身份、规范化命令／argv、工作目录、参与执行的输入文件摘要、策略 revision、创建／到期时间。Agent 品牌与会话标签单独标注可信来源，不能把自报品牌当作授权依据。涉及内容文件的参数不能只绑定路径；审批后文件变化应使批准失效。

### 12.2 单次执行与恢复

```text
submitted → denied
          → waiting → rejected / expired / cancelled
                    → approved → dispatching → running → succeeded / failed / unknown
```

- `approved` 不是成功，也不是已经启动。执行许可只消费一次；重复点击、重复传输相同请求 ID、迟到回复不会启动第二次。
- 请求自创建起 5 分钟到期。到期或 CLI 明确取消时，未启动请求作废；等待中的调用结束（内联等待返回、Agent 的调用超时）**不**使请求作废，在到期前仍可用 `wait` 接上。批准后的执行许可只能由带原 `requestId` 的 `wait`／内联等待消费；到期前无人来取则作废，不由 GUI 代为执行，也不在下一次启动后续跑。
- 消费许可前重检资源、环境、身份、输入摘要及策略 revision。切回只读、撤回资源、停用目标、换账号或改命令后，旧批准不继续使用；按新状态重新发起请求，不能静默扩大原批准。
- 明确退出时，尚未启动的审批请求取消；不能把退出视为「允许全部」。新请求在退出后按 D10 走无 CloudLink 检查路径，两者不能混在同一次重试里。
- 子进程成功创建后才确认已启动。启动失败与远端返回非零退出码分开记录；连接断开且不能确定远端状态时为 `unknown`，不给自动重跑按钮制造重复副作用。
- 不承诺跨崩溃的 exactly-once；采用最多启动一次、结果未知不自动重试。原始输入中可能含秘密的命令只短暂留在所需进程内存，持久化只保存脱敏后的审计字段，不落盘待重放命令。
- 对话框、按钮和卡片保持 D12 的既有交互。后台事件按 revision 更新，不让晚到的 `waiting` 覆盖 `cancelled` 或完成状态。
- 用户已点「允许一次」但 Agent 还没回来取时，卡片如实显示「已允许，等 Agent 继续」，到期未取显示「已过期，未执行」；这两句沿用卡片现有的状态文字位置，不加新模块。

## 13. Skills 底层分发：父级链接解析与多 Agent 共享收敛

对标 Magpie（`internal/library/skills.go:347-514`）与 CC Switch（`src-tauri/src/services/skill.rs:564-648`），在 `src-tauri/src/deliver/` 内部解决，**不新增前端 UI 目录行或确认弹窗**：

### 13.1 父级 `skills` 目录解析与叶子安全边界

- **替换 `reject_link_ancestors` 的父目录一刀切禁令**：在 `deliver/paths.rs` 中将目标检查拆分为「父目录解析」与「叶子目录校验」两步：
  1. **父目录 `target.path`（如 `~/.claude/skills`、`~/.trae/skills`）**：允许其本身或其上层祖先是符号链接或 Windows Junction（`FILE_ATTRIBUTE_REPARSE_POINT`）。逐级解析父目录的真实目标路径（设置最大解析深度 40 防止循环链接，并校验解析后的真实父目录不与 CloudLink 数据根、编译源目录或 `~/.ssh` 目录重叠）。
     - **只解析一次，之后只用真实路径**：解析得到 `real_parent` 后，后续的检查、暂存、交换全部在真实路径上进行，并对真实路径沿用现有 `reject_link_ancestors`（真实路径上不应再有链接）。交换前重新解析并比对，结果变了就中止，避免解析后链接被改指。
     - **隔离约束对真实路径重验**：`CLOUDLINK_HOME` 等隔离模式下，`real_parent` 必须仍在覆盖根（数据根、覆盖的用户目录、覆盖的 WSL 根）之内，否则拒绝。不能让测试里的一个 Junction 把写入带到真实的 `~/.claude/skills`。
     - 解析后的目录还要与其他已登记目标的真实目录比较：相同则进入第 13.2 章的共用组，互相包含（一个是另一个的子目录）则按路径异常拒绝。
  2. **叶子目录 `<real_parent>/cloudlink-servers` 及其内部文件**：严格保留 `symlink_metadata` + Windows `FILE_ATTRIBUTE_REPARSE_POINT`（`0x400`）与 `.cloudlink.json` 所有权校验。若叶子本身是外部软链接／Junction 或无 `.cloudlink.json` 的同名目录，判定为真实的 `DeliveryStatus::Conflict`（需用户点「备份并接管」），绝不跟随叶子链接覆写或删除外部目录。
- **区分真实冲突与写入错误**：父目录悬空链接、循环链接或 I/O 权限错误不再映射成 `DeliveryStatus::Conflict`（「目录里已有同名 Skill」），而是返回 `DeliveryStatus::Broken` / 具体错误原因。
- **同目录暂存交换与回滚**：更新受管副本时，在真实父目录下先写临时副本并校验，再替换旧受管副本（参考 Magpie `skills.go:200, 594`）；失败时恢复旧副本。

### 13.2 多 Agent 指向同一真实父目录的底层收敛（Magpie `sharers` 模式）

- 在 `deliver::sync_auto` / `publish_locked` 中，按同一运行环境内解析后的真实父目录（`real_parent`）对已启用的目标分组（对应 Magpie `skills.go:465-503` 的 `sharers`）。按 D13，一个组是一个分发单位：
  - **开关对整组生效**：`set_distribute` 给组内一个 Agent 开启或关闭某项资源时，同一事务里对组内全部已启用成员做同样修改，返回值带上受影响的成员，前端据此点亮图标并提示「X 与 Y 共用同一目录，已一起提供」。组内成员的资源选择因此始终一致，不存在「取并集」。
  - **发现共用时先对齐**：升级后或用户新建链接后首次发现共用，而成员的选择不一致时，不静默扩大：先按各成员选择的交集写入，并在 Agent 页该行现有的状态位置提示「与 X 共用同一目录，资源选择不一致」，由用户在任一成员上开关一次即对齐。
  - **一份编译产物、一份副本**：现有标记是 `env_id + agent_key`（`compile/publish.rs` 的 `Marker`），编译产物也按这两项分目录。共用组编译一份，标记新增可选的 `agent_keys` 列表记录组内全部成员；模板内容目前不因 Agent 而异，实施时再核对一次，若有差异须定共用目录用哪一版。
  - **旧标记兼容**：副本上的旧标记只有单个 `agent_key`，只要它属于当前组内任一成员就视为受管，下次写入时升级为新格式，不报同名冲突。标记属于组外的 Agent 或格式非法仍按冲突／损坏处理。
  - **全部不需要时才移除**：组内全部成员都停用，或已无列入资源时才移除副本；停用其中一个成员不移除，Agent 页在该成员行如实说明目录仍由共用的另一个 Agent 使用。
- **真实写入反馈**：`set_distribute` 与 `set_target_enabled` 根据目标的实际 `DeliveryStatus` 返回结果；若目标处于 `Conflict` 或写入失败，前端如实提示原因，不再无条件弹出「已同步」成功 Toast。

### 13.3 WSL 目标

- **在发行版内解析**：WSL 目标经 UNC 路径访问，Linux 的绝对符号链接不能靠 Windows 侧的路径解析得到正确结果。WSL 目标的真实目录在该发行版内解析（等价于 `realpath`），沿用现有的 WSL 调用方式，不新增依赖；解析失败返回具体原因，不映射成同名冲突。实施时先在隔离的 WSL 根里用真实符号链接验证这一点。
- **链到 Windows 目录（D15）**：解析结果落在 `/mnt/<盘符>/…` 且对应某个 Windows 目标的真实目录时，只由 Windows 侧写入；WSL 目标状态为「与 Windows 共用目录，未单独提供」，不写入、不报冲突、不参与第 13.2 章的分组。Agent 页该行如实显示这一状态，并说明该目录里的 Skill 是按 Windows 环境写的。
- **链到其他位置**：落在 `/mnt/` 下但不对应任何已登记目标，或落在其他挂载点、另一个发行版时，返回具体的不支持原因，不尝试写入。

## 14. GitHub 与旧数据迁移

### 14.1 归属、登录身份和动态范围分开存储

新增 GitHub 专属配置：固定 GitHub host、稳定 owner ID 与当前 login、owner 类型、`auto | manual`、手选 repo IDs、排除 repo IDs、分环境身份与发现快照状态。v0.3 不把这一改动强加给其他三个 CLI 的账号模型。

- 同一 host / owner 只有一项 GitHub 资源；同一登录身份可以供多个 owner 使用。显示名称默认仍为 GitHub，身份不拼进主标题。
- owner、仓库的重命名按稳定 ID 跟踪；转移到未选 owner 后不能无提示继续纳入。排除不会因名称变化失效。
- 自动模式为「这个 owner 下当前及未来有权访问的仓库，减排除项」；手动模式只取已选稳定 ID。公开仓库、私有仓库、分页不完整与暂时无权访问要分清。
- 详情按需刷新，自动刷新节流建议 30 秒；手动刷新可立即执行。失败保留快照，状态为 partial / offline / denied，不能据缺失列表推断删除。
- CloudLink 运行时，实际写操作要重新核对有效身份、目标稳定 ID、owner 与范围，不能把 UI 缓存当作授权。查询接口也按子命令／端点分类，不能把全部 HTTP GET 当作安全查询。
- 退出后仍可按配置发现和组织仓库信息，但这不再是 CloudLink 的强制命令范围检查；用户现有 gh 凭据可能访问更多资源，按 D10 如实说明。
- 仓库 → 部署关系记录证据来源。关系不改变生产标记、档位或授权；未提供的资源和 remote URL 中的凭据不得经关系文本泄漏。

### 14.2 迁移不扩大范围

- 旧 GitHub 手选记录迁为 manual，保留 repo IDs；没有明确选择自动跟随前不纳入未来仓库。
- 若旧记录包含多个 owner，先按可核实的归属提出拆分计划，保留原来的档位与选择范围，不把登录身份误当 owner。归属无法核实时保留待确认，不猜、不丢历史数据。
- 新服务器的默认名称与别名均不含地址。历史显示名称疑似由地址生成时，给出修正建议并由用户确认，不批量改名，不改用户原 SSH 配置。
- Skill 文件名及执行路由可以使用现有稳定资源 ID 派生的内部引用，避免为隐藏 IP 而破坏旧手动别名。旧别名含地址时不把它当作「匿名」导出；必要时用独立调用入口保留其私有映射。显示名称仍含禁止导出的地址时，要求用户修正名称，不关闭隐私检查。
- 数据库迁移版本取实施时最新 `schema_version` 的下一版，不硬写当前观察到的版本号。

## 15. IPC、事件与诊断契约增量

以下为建议的新接口名，实施时统一登记 Rust、ts-rs、手写契约检查、Mock 和前端封装；不在组件中直接 invoke / listen。

| 接口 | 输入 → 输出／作用 |
| :--- | :--- |
| `getGithubScope` / `saveGithubScope` | 归属绑定、模式、稳定 repo IDs、expectedRevision；保存不直接冒充送达成功 |
| `listExecutionRequests` | 当前会话待处理与最近请求，不返回可重放的敏感原始命令 |
| `respondExecution` | requestId、allow-once／deny、expectedRevision；仅 GUI 路径可批准 |
| `cancelExecution` | 取消自己仍未启动的请求；不声称回滚远端副作用 |
| `getRuntimeStatus` | GUI 当前 session / starting / active / stopping 状态及实际覆盖能力 |

- 保留现有 `saveAsset`、`setDistribute`、`setTargetEnabled` 等入口，底层统一走父目录解析与 `sharers` 收敛逻辑，并在返回结果中携带最新 `DeliveryStatus`，使前端据此判断是否真正写入成功。
- 新事件建议为 `execution://changed`、`runtime://changed`；现有 `deliveries://changed` / `operations://new` 保持不变。
- `Operation` 保留原 `allowed | denied`，增加来源、是否实际检查、执行状态、requestId、退出码与耗时等可选字段。旧 hook 记录只能显示已放行／已拦截；没有退出码不能推断执行成功。
- 在 `ConnectionTestedEvent` 和必要的 `KeyCheck` 中增加可选 `ConnectionDiagnostic`：阶段、现有错误 ID、客户端种类／版本、退出码、允许显示的 reason ID / 参数。`SshErrorId` 继续使用 `auth-failed`、`password-rejected`、`host-key-changed`、`key-permissions`、`unknown` 等现有值。
- 诊断参数使用白名单，不塞任意 stderr、用户名／地址拼接串、密码、私钥、原始探测输出或执行输入。只复制界面已经展示的安全摘要，未知错误不再指向无内容的日志。
- `copyKeyToSshDir` / `copyKeyToWsl` 沿用原命令与明确确认；不新增修改原私钥 ACL 的接口。保存凭据的 `PasswordTargetChanged` 检查与测试禁用 OS 凭据库不变。

## 16. 传输、长任务与失败收敛

### 16.1 文件与长任务

- v0.3 的 put / get 只支持单文件、只写到**不存在的新路径**，不递归展开通配符、不默认恢复断点、不创建远端常驻服务。使用系统 OpenSSH 的 SFTP 批处理能力；路径空格与 glob 元字符分别引用／转义，禁止控制字符及批处理命令注入，失败即停止，不使用忽略错误前缀。
- 目标已存在即失败，不提供覆盖选项。下载用本地的排他新建写入，不跟随本地 symlink / reparse point。上传前检查远端目标不存在；检查与写入之间有极短的竞态窗口，文档如实说明，定位是防手滑，v0.3 不做硬链接发布、私有暂存目录这类排他发布机制。只清理本次创建的未完成文件，不清理用户目录。
- CloudLink 运行时，上传按写操作判断，下载仍检查凭据路径与作用域；只读档不因传输入口而获得写权限。需要替换既有远端内容时，可先上传新路径，再发起单独、明确的替换命令接受档位／风险判定；不在传输接口中悄悄附送覆盖、删除或清理。
- 审批绑定上传输入的内容摘要，执行前重新核对；文件变化使批准失效。数据流不写进操作记录或 Skill。
- foreground exec 默认 90 秒（低于常见 Agent 单次调用约 2 分钟的上限），允许显式设置至 3600 秒；Skill 里写明：预计超过默认时间的命令用后台启动加轮询，或同时调大 Agent 自己的调用超时。连接建立仍使用短连接超时。超时或断线后终止本地进程，不承诺远端工作已停止；结果无法确认则 unknown，不自动重试。
- 长任务沿用 Agent 自行启动后台任务并轮询的约定，不新增桌面任务管理器。CloudLink 运行时，包装命令仍须能按真实内容解析；不能以 `nohup` 或脚本包装跳过检查。生产只读档也不能借后台启动进行写入。

### 16.2 跨数据库与文件的收敛

- 模式、范围等变更有单调 revision；策略与路由更新独立于 Skill Lint。运行中策略失效不能被旧 Skill 的成功快照掩盖。
- 收窄授权时优先收紧运行策略，无法安全保留的旧受管副本撤回；不得继续以旧副本暴露已撤回的资源。
- 每个真实父目录串行发布；对单个目录的新源做校验、Lint、暂存、叶子所有权／重解析点重检和交换；失败保留旧内容并返回具体状态。
- 晚到的探测、同步、审批与刷新结果必须比较资源／范围 revision 和会话 epoch。删除或重置之后，旧任务不能恢复资源、副本、授权或待执行请求。
